# CH32V203C8T6 (nanoCH32V203) bring-up

First non-ESP32, first non-Tensilica, 4th-architecture target for the
ComposeUX reactive tier — after ESP32 (Xtensa LX6), ESP32-S3 (Xtensa LX7),
and ESP32-C3 (RISC-V), this is the **second RISC-V core** and the **first
WCH / QingKe** part. It is a *different toolchain and flash mechanism* from
every ESP32 board in this repo — no `esptool`, no `idf.py`, no auto-reset
DTR/RTS dance. Read this whole doc before touching the board; the ISP entry
step is manual and easy to get wrong on the first try.

Sources: `firmware/ch32v203_bringup/platformio.ini`, commit `83f7a58`
("CH32V203 bring-up: toolchain proven + blink on the nanoCH32V203"), and
hardware verification performed 2026-07-10.

## Identity

- **Chip**: CH32V203C8T6 — WCH QingKe V4B core (RV32, RISC-V), silicon ID
  `0x3119`. Datasheet-marked **64KB flash / 20KB RAM**.
- **Clocks**: 8MHz HSE crystal (PLL source) + 32.768kHz LSE crystal
  (RTC/backup), PLL'd to **144MHz** system clock. `SystemInit()` (Arduino
  core startup) does the PLL bring-up; `delay()` is SysTick-calibrated to
  `SystemCoreClock`, so `delay(250)` is really 250ms once the PLL is
  running.
- **Board**: MuseLab (wuxx) **nanoCH32V203 v1.1**. Two USB-C ports — only
  one is the MCU's native USB (D+/D- on PA11/PA12); the other is
  power/aux, don't confuse them. One **BOOT** momentary button (this is
  BOOT0, not reset).
- **Why this chip**: the WCH-sweep "cheap first-class-CAN" pick for the
  reactive embedded tier — CAN transceiver bring-up is a later pass,
  pending hardware.
- **Not an ESP32**: there is no `esptool`, no serial auto-download circuit.
  Flashing is a **USB-ISP bootloader** reached by a manual strap
  (BOOT0 held during reset), flashed with `wchisp`, a Rust CLI.

## Toolchain install (one-time, macOS)

Two independent toolchains are needed: the WCH USB-ISP flasher (`wchisp`,
installed via Cargo) and the PlatformIO build platform (`ch32v`, installed
via `pio`). Neither depends on the other.

```bash
# 1. wchisp (flasher) — needs libusb + a working Rust toolchain.
brew install libusb
rustup default stable   # GOTCHA: rustup may have no default toolchain set;
                         # `cargo install` silently fails/misbehaves without this.
export PKG_CONFIG_PATH="$(brew --prefix libusb)/lib/pkgconfig:$PKG_CONFIG_PATH"
cargo install wchisp --locked
# binary lands at ~/.cargo/bin/wchisp
```

PlatformIO side: `platform = ch32v` pulls **Community-PIO-CH32V**
automatically on first `pio run` — no separate install step, but see the
gotcha below.

**GOTCHA — stale package-install lock**: a stale `pio pkg install -g -p
ch32v` process can be caught mid-way through deep-cloning the **Windows**
variant of the toolchain (wrong OS) and holding PlatformIO's package lock.
Symptom: a `pio run` that stalls indefinitely with empty/no output. Fix:
find and kill the stale `pio`/`pip`/git-clone process, then retry.

## The BOOT/ISP dance (every reflash)

The CH32V203 only exposes a flashable USB-ISP interface while sitting in
its ROM bootloader. User firmware does not expose it. Every single reflash
requires manually re-entering ISP mode first:

1. **Hold BOOT0** (the BOOT button on the nanoCH32V203).
2. Tap **reset** while still holding BOOT0 (or unplug/replug USB while
   holding BOOT0 if there's no separate reset button in reach).
3. Release BOOT0.

The chip now enumerates as a **WCH ISP** USB device:

```
VID:PID = 4348:55e0
```

Confirm before flashing:

```bash
system_profiler SPUSBDataType | grep 0x55e0
```

If that grep is empty, the chip is **not** in ISP mode — redo the BOOT0
strap. Once user code runs (post-flash, after the automatic reset), the
4348:55e0 ISP interface disappears; the chip re-enumerates as its own
native CDC device instead (see below). There's no way to force ISP mode
from software alone on this board — it's a physical strap every time.

## Build + flash

```bash
cd firmware/ch32v203_bringup
pio run -e nanoCH32V203              # or -e ch32v203_dsl_test
export PATH="$HOME/.cargo/bin:$PATH"
wchisp flash .pio/build/nanoCH32V203/firmware.bin
```

`wchisp flash` writes, **verifies**, and resets-to-run automatically — no
separate verify or reset step needed. The chip must already be strapped
into ISP mode (previous section) before this command; `wchisp` does not
drive BOOT0 itself (unlike `esptool`'s auto-reset, there is no DTR/RTS
trick here — it's a hardware-only gate).

## The >64KB "extra flash" gotcha

The datasheet marks the C8T6 as 64KB flash, but the die **physically
carries more** (the well-known CH32V203 "extra flash" — commonly ~128KB).
`board_upload.maximum_size = 131072` in `platformio.ini` targets that
extended region so a larger image links and runs.

This was exercised for real: the on-chip DSL-corpus test build
(`ch32v203_dsl_test`) is **82.8KB** — about 18KB over the datasheet 64KB
limit even after aggressive trimming (`-fno-unwind-tables`,
`-fmerge-all-constants`, TinyUSB class stripping, `lib_ignore`). `wchisp`
wrote **and verified** the full 82KB image clean on this specific unit.

**Caveat — this is not a guaranteed spec, it's a per-unit fact**: extended
flash beyond 64KB is real silicon margin, not a datasheet commitment.
Verify each new unit before relying on >64KB images (flash + verify a
build that lands in the 64–96KB range and confirm `wchisp` reports a clean
verify). If a unit doesn't have the margin, the fallback is either a
larger-flash CH32V203 variant (RB = 128KB **official**, same `platformio.ini`
env otherwise) or a size-reduced build.

## Post-flash serial / CDC

Blink-only builds (`env:nanoCH32V203`) have no serial console. Builds that
pass `-D PIO_FRAMEWORK_ARDUINO_USBD` (e.g. `ch32v203_dsl_test`) bring up
the **native USB CDC** (openwch TinyUSB, `Serial`) after reset:

```
VID:PID = 1a86:8010
```

This enumerates as a **new** `/dev/cu.usbmodem*` device (different from
the 4348:55e0 ISP interface, which is gone by this point). Read at
**115200** baud, e.g. `pio device monitor -e ch32v203_dsl_test` or
`screen /dev/cu.usbmodem* 115200`.

## Verify: DSL conformance (231/234)

`env:ch32v203_dsl_test` re-runs the **same 234-case [SPEC:CXC-DSL]
conformance corpus** used on the ESP envs, compiled by reference
(byte-identical, never forked) from `cyd/src` + `cyd/test` via
`dsl_reuse.py`. Result on real CH32V203C8T6 hardware:

- **231/234 passed.**
- **All soft-`double` / IEEE-754 float cases passed** — bit-exact
  soft-double confirmed on a **third independent RISC-V toolchain** (after
  ESP32-C3's RISC-V and the Xtensa LX6/LX7 cores). This is the load-bearing
  result of this bring-up: the DSL's numeric semantics do not depend on a
  specific vendor toolchain.
- **All 3 failures are in `canon_equality`** — string↔bool/number
  canonicalization (`1=='on'`, `'off'==0`, `ns('d')==1`). **Not** float,
  not soft-double.

**Why this points at the WCH toolchain, not RISC-V itself**: the ESP32-C3
is also RISC-V and passes all 234/234. So the divergence is specific to
the WCH GCC/newlib toolchain, not a RISC-V-generic issue. Leading
suspects: GCC's `char` signedness default on this target (WCH's `riscv-
none-elf-gcc` may default `char` to unsigned where the ESP toolchains
default to signed), or a newlib string/parse difference reached only by
the canon-equality path.

**Optimization constraint**: soft-double bit-exactness requires staying at
`-Os` (the core default). Do **not** enable `-Ofast` or `-ffast-math` on
this or any DSL-corpus env — either would break the bit-exactness proof
this test exists to establish.

## Known issues / follow-ups

1. **`canon_equality` WCH-toolchain divergence (3/234, open)** — not yet
   fixed. Likely fix is a build flag (try `-fsigned-char` first) or a
   small tweak in the canon-equality code path itself. Confirm with a
   targeted rebuild + reflash once a fix is tried; do not assume fixed
   without re-running the corpus on hardware.
2. **Per-unit >64KB flash verification** — the 131072-byte
   `maximum_size` override relies on silicon margin that is not
   datasheet-guaranteed. Any new physical unit running an image over 64KB
   needs its own clean-verify confirmation via `wchisp flash` before being
   trusted. Keep the 128KB-official RB variant or a size-reduced build as
   the documented fallback.
3. **CAN transceiver bring-up** — this chip was picked for
   first-class CAN; that step is pending hardware and not yet attempted.
4. **`src/main.cpp` is throwaway** — the register-level all-GPIO blink
   exists only to prove the toolchain end-to-end and will be replaced by
   the reactive-core port (namespace store + bindings + on-chip DSL).
