# TM1637 — 4/6-digit 7-segment LED driver

**[PLACEMENT UNRATIFIED]** — a PERIPHERAL descriptor, the first in this directory.
The machine-readable view is `tm1637.descriptor.yaml`; this is the human one.

**Status: HOST-PROVEN ONLY. There is no TM1637 on any bench.** 108 host checks pass;
every one of them is about arithmetic and waveform *shape*. Nine things need a lit tube
and David's eyes, and they are listed at the end — not as a formality, but because this
part's failure mode is a display that is confidently, well-formedly **wrong**.

Everything below cites Titan Micro TM1637 datasheet **V2.4** by page.

---

## 1. Can they be daisy-chained? No — and the pass-through headers are not what they look like

**They cannot be independently addressed on two shared wires, because the part has no
device address at all.** The datasheet says so outright, parenthetically, on p.3:

> "Microprocessor data realize the communication with TM1637 by means of two-wire bus
> interface (Note: The communication method is not equal to I2C bus protocol totally
> **because there is no slave address**)."

The only "address" in the whole command set is the **display register** address `C0H..C5H`
(p.5), which selects a **digit within one chip**. There is no chip-select, no address byte,
no addressing phase.

**The pass-through headers are wiring convenience, and the proof is an absence.** The pin
list (p.1 pinout, p.2 pin functions) is twenty pins: GND, SEG1-8/KS1-8, GRID1-6, VDD, DIO,
CLK, K1, K2. **There is no serial-out pin of any kind.** A MAX7219 chains because it has
`DOUT`; this part has nothing to chain *into*. The headers bus four nets — VCC, GND, CLK,
DIO — along a row so modules can be butted together mechanically.

> ⚠ **One line in the datasheet looks like evidence of a chain and is not.** The p.9
> electrical table carries a row *"DOUT pin output low current, Idout, 4 mA min, Vo=0.4V,
> dout"* — but no DOUT pin exists in the pinout or the pin-function table. It is the DIO
> pin's output-low drive (used for ACK and key-read data), mislabelled: a copy-paste
> artifact of Titan Micro reusing tables across the TM16xx family. Recorded because anyone
> hunting for chaining support will find it and take it as confirmation.

**Fully-shared CLK+DIO is a legitimate topology — for mirrored displays.** With no address,
both parts latch every command and show identical content. That is the *only* thing two
shared wires can express. Use it deliberately (a value readable from two sides); never
expect independent content from it.

## 2. The workable topology: shared CLK, one DIO per display

**N displays = N+1 host pins.** This is the recommendation.

**Why it works.** p.3 defines the start condition as an edge on DIO, gated on CLK:

> "When CLK is a high level and DIO changes from high to low level, data input **starts**."

A display whose DIO never moves is never armed, so clock traffic addressed to a sibling is
not data to it. Two further facts turn "probably fine" into "safe":

1. **Display refresh runs off the internal RC oscillator** (fosc typ 450 kHz, p.10), **not
   off CLK**. An unaddressed part keeps multiplexing its digits out of its own SRAM
   regardless of what the clock line does. There is no clock-starvation state to fall into.
2. **Every transaction is bracketed by a START on that part's own DIO**, and p.4 states that
   a STOP *"initializes serial communication"*. So even under the pessimistic assumption
   that some die counts clock edges without a start, each transaction **resynchronises** it.
   Damage from a phantom bit is bounded by one transaction rather than being permanent.

### ⛔ The obligation that makes it true

**A non-selected DIO must be parked HIGH and never touched.** Pulling an idle display's DIO
low while CLK is high **is a start condition** — it would arm that display, and it would then
latch the next eight bits meant for its neighbour. Selection is *"drive exactly one DIO,
leave the rest released"*. The driver's open-drain seams make this structural: it only ever
owns one pin set at a time.

### ⛔ What the datasheet does *not* say

There is **no sentence** reading "a part with a static DIO ignores CLK", and there is no
state diagram. The claim above is a **strong inference from the stated start condition, not a
verbatim guarantee**, and it has not been checked on a part. Treat it as designed-and-argued,
not proven — the harness test in §7 is what would falsify it.

### The fallback, recorded so it is not re-derived under bench pressure

If the inference is ever falsified, use **shared DIO + one CLK per display**, with
non-selected CLK parked **LOW**. Same pin count (N+1), and **mechanically stronger**:
latching is defined on the CLK **rising** edge (p.2, CLK: *"used for data input and output
at rising edge"*), so a part whose CLK never rises **cannot latch a bit at all**. The gate is
on the latch itself rather than on start detection.

Its costs, which are why it is the fallback and not the default: all parts share the ACK
line, so one wedged part holds DIO low for everyone; and selection may only change while DIO
is idle high (raising a parked-low CLK while DIO is low would clock a phantom bit).

## 3. How many on one shared clock? Pins and the 5 V rail, not the bus

The intuition that bus capacitance limits the count is **wrong here**, and the reason is
worth knowing.

Each module carries the datasheet's reference network (p.8): a **10 kΩ pull-up** on each line
**and** a **100 pF** cap to GND, plus the die's own **15 pF** input capacitance (CI, p.10).
So each module adds ~115 pF **and** a parallel pull-up. On a shared CLK with N modules:

```
R_eff = 10k / N        C_eff = 115N pF + C_wire

tau = R_eff * C_eff = 10k * 115pF  +  (10k * C_wire) / N
                    = 1.15 us      +  (a term that SHRINKS as N grows)
```

**The time constant is essentially N-invariant, and actually improves with N** — adding a
module adds capacitance and stiffens the pull-up in equal measure. With ~80 pF of harness:

| N | τ | rise to VIH (1.204 τ) | low-side sink |
|---|---|---|---|
| 1 | 1.95 µs | 2.35 µs | 0.5 mA |
| 2 | 1.55 µs | 1.87 µs | 1.0 mA |
| 4 | 1.35 µs | 1.63 µs | 2.0 mA |
| 8 | 1.25 µs | 1.50 µs | 4.0 mA |

Sink current is trivial at any count. **The driver's default 5 µs half-period (100 kHz) has
~3× margin over the rise time at every N in that table**, which is why it is the default —
slack bought for free, since a 4-digit refresh is ~50 clocks ≈ 500 µs and no bus namespace
changes anywhere near that fast.

**What actually limits the count:**

- **Host GPIO.** On an ESP32-C3 Super Mini: ~13 exposed, less strapping pins GPIO2/8/9, less
  the console UART, less anything else the board carries. Realistically **4-6 displays**.
- **The 5 V rail.** A 4-digit module draws roughly **20-80 mA** depending on brightness. Four
  modules at full brightness can ask for **~320 mA**, which on a board with a small LDO is
  the real constraint. Brightness step 0 (1/16 duty) is the cheap end of an 8× range.

> If pins become the binding constraint before power does, note the fleet pattern already
> recorded for `rack_triple_gauge`: an I²C expander buys pin headroom. But bit-banging DIO
> *through* an expander is slow, and at N+1 pins the direct wiring is cheap. Prefer more pins.

## 4. Electrical: both lines are open-drain, and 3.3 V hosts have an unmade decision

**The driver never drives either line high.** That is not stylistic:

- The chip **drives DIO low itself** to ACK (p.3, 8th falling edge). A master actively
  driving DIO high during the ACK window is a supply short through two output stages.
- **VIH min is 0.7×VDD** (p.10) = **3.5 V at VDD=5 V**. A 3.3 V push-pull high **does not
  reach it**. Open-drain + the module's own 10 kΩ pull-up takes the line to 5 V and the spec
  is met — a second, independent reason to never drive high.

> ⚠ **THE CONVERSE HAZARD IS REAL AND THE DECISION IS UNMADE.** A released line sits at
> **5 V**, and an ESP32 GPIO is **not 5 V tolerant**. Three options: level-shift; add a series
> resistor; or run the TM1637 at **VDD = 3.3 V** (VIH becomes 2.31 V, comfortably in spec) at
> the cost of brightness — and p.8 note 3 warns that blue/white tubes will not light at 3.3 V
> at all: *"Since blue-ray nixie tube break over step-down voltage is 3V, TM1637 power supply
> should be 5V."*
>
> **This must be settled before a harness is soldered.** It is a board decision, not something
> the driver can fix, and which tube colour David's panel uses decides it.

## 5. Protocol, as implemented

Nine clocks per byte, **not eight** — the ACK is a ninth (p.3). LSB first. Data changes while
CLK is low; latched on the CLK **rising** edge.

| command | value | page |
|---|---|---|
| data write, auto-increment | `0x40` | p.4 |
| data write, fixed address | `0x44` | p.4 |
| read key scan | `0x42` | p.4 |
| set digit address | `0xC0 \| 0..5` | p.5 |
| display control | `0x80 \| bright(0..7) \| 0x08 if ON` | p.5 |

**Brightness is eight steps and they are not linear**: pulse widths 1/16, 2/16, 4/16, 10/16,
11/16, 12/16, 13/16, 14/16 (p.5). There is no 3/16 and no 5..9/16. A bus brightness *fraction*
therefore maps to a **step index**, never to a duty cycle — the driver does this explicitly.

**Timing floors are enforced in code, not documented in comments** (p.10): CLK high ≥ 1 µs
(tWAIT — the binding constraint; PWCLK 400 ns and tSETUP/tHOLD 100 ns all follow from it),
Fmax 500 kHz. **Key reads carry a separate, slower ceiling of 250 kHz** (p.3), so
`tm1637_read_keys` temporarily slows down and restores the write rate afterwards. A caller
asking for something too fast is **clamped, and the clamp is recorded** in
`timing_was_clamped` — a silent clamp is a limit that lies about having been hit.

**The auto-increment write is one frame.** p.4 diagram 2: the address command and all N data
bytes share a single START..STOP. The address auto-increments *only within a frame*, so
splitting the data run rewrites digit 0 N times — a bug that displays a plausible single
digit rather than obvious garbage. Pinned by a three-frame assertion in the self-test.

## 6. Where the value → digits decision lives, and why

**Formatting is a BACKEND concern.** Per `[CXC-VISION-SEMANTIC-REALIZATION]`, the widget is
semantic and the backend is the realization. The bus carries a value; how many digits it
occupies, whether it is right-justified, whether the pad is blank or zero, and where a decimal
point physically goes are properties of **this surface**. A publisher that had to know it was
feeding a 4-digit tube would have leaked the realization back onto the bus — the exact
coupling `DP-CIO-6` exists to prevent.

**The policy, and it is deliberately the same as the raster widget's**
(`python/composeio/render/widgets/seven_segment.py::_display_value`):

- the semantic value is a **string**;
- **right-justified** into the digit count;
- short values pad **left with blanks, not zeros** — a blank-padded `42` reads as forty-two,
  a zero-padded `0042` reads as a different quantity and the widget contract has no field
  saying which was meant;
- long values keep the **rightmost** digits, because dropping the high end of an over-range
  reading is a visible nonsense while dropping the low end is a plausible wrong number.

**Choosing the same policy as the raster surface is the whole point**, and it is enforced by a
parity corpus generated from the Python widget: the same namespace must *read the same* on a
480×320 panel and on a tube, or "one semantic value, many realizations" is a slogan.

> ⚠ **Where the two realizations genuinely cannot match — and this is a finding for the I2
> decision, not a detail.** On the raster widget `.` and `:` each consume their **own narrow
> cell**. A TM1637 has no cell to give them: a `.` folds into the **preceding digit's dp bit**
> and `:` into whichever single bit the module wires the colon to. So `"12.34"` is **five
> cells on a panel and four digits on a tube**. **`digits` is not a portable count across
> realizations**, and any scene format carrying a digit count is carrying a raster-shaped
> number.

**Three channels, not one value.** The binding subscribes `value`, `brightness` and `power` as
three independently addressable actuators on **one** widget. A single-value widget contract
has nowhere to put the latter two — which is the same shape as the gauge cluster's
`{needle + illumination}`, and is the substance of the I2 decision.

## 7. Bring-up

```bash
# Regenerate the parity corpus from the raster widget (the oracle)
python3 python/scripts/gen_tm1637_corpus_header.py

# Build + run the host suite
cd cyd && pio run -e native_tm1637 && ./.pio/build/native_tm1637/program
# Must print ALL PASS and exit 0.  108 checks as of 2026-08-14.
```

**What the suite is, in four independent layers.** A bit-banged display driver is this
repo's worst case of self-confirming evidence, so no layer is allowed to be the only witness:

1. **Glyph parity** against `seven_segment.lit_segments()` — the oracle is the **raster
   realization**, not a C++ round trip. Encoding and decoding with the same code passes with a
   fully **permuted** segment table, because both halves make the same mistake.
2. **Justification parity** against `SevenSegmentDisplay._display_value()`. Cases span
   shorter-than / exactly / longer-than the surface — *a corpus of only exact-fit cases cannot
   tell right-justification from left-justification.*
3. **Waveform** — a golden transaction transcribed **by hand from the datasheet prose**, not
   captured from the driver, plus generic p.3 invariants (DIO moves only while CLK is low
   except START/STOP; CLK high ≥ tWAIT; whole 9-clock bytes) checked over every transaction.
4. **Negative controls** — four deliberately corrupted traces the checker **must reject**,
   plus a paired check that it still **accepts** a valid one. `[CXC-VISION-EPISTEMICS]`
   rule-negative-control: an instrument that can only report success is not an instrument.

**All three instruments were mutation-tested and are load-bearing:** an MSB-first bit order is
caught by the golden *and* by the independent byte decoder (`0x8F` read back as `0xF1`); a
one-segment change to the truth table is caught by the parity corpus.

**The checker had a real off-by-one on first run**, worth recording: the STOP sequence
contributes a CLK rising edge of its own (a stop is *DIO rises while CLK is high*, so CLK must
be taken high first), so every frame counted 10 rising edges rather than 9. Subtracted
explicitly rather than fudged into the modulus.

## 8. ⛔ What needs a lit tube and David's eyes

**Nothing here has been done. Every item is in the class where a machine signal exists and
agrees with the wrong answer.** Ask about *specific glyphs*, never "does it look right".

1. **Segment map** — display `0`. All six outer bars lit, centre bar **dark**? If any single
   bar is wrong the map is permuted; note **which** bar.
2. **Segment map, discriminating** — display `1`, then `7`. `1` must light the two
   **right-hand vertical** bars only; `7` must add the **top** bar. If `1` lights two bars on
   the **left**, then b/c are swapped with e/f.
3. **Digit order** — display `1234`. Is the **leftmost** tube showing `1`? If it shows `4`,
   GRID1 is the rightmost and the buffer needs reversing.
4. **Justification** — publish `42` to a 4-digit surface. Expect **two blank tubes, then 4,
   then 2**. Not `42  `, and not `0042`.
5. **Decimal point** — display `12.34`. Expect exactly **four** lit tubes with the point after
   the 2 — five characters in four digits.
6. **Brightness** — step 0, then step 7. Both must be **visibly lit** and clearly different;
   step 0 is 1/16 duty and is **dim, not off**.
7. **Display off** — the OFF command must blank **all** tubes while the host keeps writing
   values. This distinguishes "display off" from "wrote zeros".
8. **Multi-display — the load-bearing one.** Two modules, shared CLK, separate DIO. Write
   `1111` to A and `2222` to B, then write A **repeatedly for a minute**. B must not flicker,
   blank, or change. Then power-cycle **only A** and repeat: B must be undisturbed. **This is
   the only test that can falsify the shared-clock inference in §2.**
9. **Negative control for (8)** — deliberately strap both DIO lines together and confirm the
   two displays go **identical**. If they do not, the harness is not what you think it is and
   test 8 proved nothing.

**Also outstanding and not an eyes question:** the 3.3 V / 5 V decision in §4, which depends
on the tube colour on David's panel.
